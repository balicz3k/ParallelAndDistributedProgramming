# ============================================================================
# topk_cuda / topk_cublas — benchmark CUDA (top-k wyszukiwanie wektorowe)
# ============================================================================
# Sprzet:   NVIDIA GeForce RTX 4060, 8188 MiB, Ada Lovelace sm_89
#           AMD Ryzen 7 5700X (8C/16T), 31 GiB RAM
# Soft:     CUDA 12.4 (nvcc V12.4.131), -O3 -std=c++17 -arch=sm_89
# Dane:     float32, D=128, Q=20 (zapytania.bin), generate_data.py seed=42
# Metryka:  odleglosc euklidesowa; remis = mniejszy indeks (jak w referencji)
#
# Poprawnosc: indeksy top-k IDENTYCZNE z referencja (topk_ref) sprawdzone dla
#   N=10k/100k/1M oraz k=1/10/20/50 (diff = 0). cuBLAS: indeksy identyczne
#   (odleglosci w ramach tolerancji FP — inna kolejnosc sumowania w SGEMM).
#
# Metodologia pomiaru:
#   - warmup=2 + repeat=5 niezaleznych pomiarow; mediana + rozrzut [min/max/IQR].
#   - czas RDZENIA (kernel_ms) oddzielony od czasu PELNEGO (total_ms, z transferem
#     H->D->H zapytan i wynikow); transfer BAZY mierzony osobno (base_upload_ms,
#     baza persystentna na GPU — wgrywana RAZ, zgodnie z karta D03).
#   - P95: query_latency_us_pXX = 95. percentyl LATENCJI POJEDYNCZEGO zapytania,
#     mierzonej zdarzeniami CUDA per zapytanie (kernel jednoblokowy na zapytanie),
#     n_obs = Q*repeat = 100 obserwacji zadan. To NIE jest kernel_ms/Q.
#   - QPS (tryb batch): caly wsad Q przez wiele blokow rownolegle, przepustowosc.
#   - VRAM: cudaMemGetInfo (alokacja = roznica free przed/po; used = total-free).
#   - RAM: getrusage(RUSAGE_SELF).ru_maxrss (peak RSS).
#
# Architektura wlasnego kernela (topk_cuda):
#   - 1 blok = 1 zapytanie; zapytanie w shared memory; baza grid-stride + float4.
#   - lokalny top-k w rejestrach (sortowana wstawka) -> REDUKCJA DRZEWIASTA
#     (merge dwoch posortowanych list top-k w O(k)); brak sekwencyjnej petli
#     w watku 0.
#   - strumienie: baza wgrana raz; transfer zapytan nakladany na kernel. Przy
#     Q=20 transfer zapytan (~10 KB) jest pomijalny -> streamy ON vs OFF bez
#     mierzalnej roznicy (obciazenie compute-bound). Mechanizm zaimplementowany;
#     zysk ujawnilby sie dla duzego Q / strumienia zapytan online.
#
# topk_cublas (druga implementacja, referencja wydajnosci):
#   - ||q-b||^2 = ||q||^2 + ||b||^2 - 2 q.b; iloczyn q.b przez cuBLAS SGEMM,
#     normy + skladanie + selekcja top-k = wlasne kernele. Materializuje pelna
#     macierz odleglosci Q*N w VRAM (dist_matrix_mb) — stad wiekszy narzut pamieci.
#
# Skroty kluczowych wynikow (mediana z 5 powtorzen, k=10):
#   N=10k:  wlasny kernel 0.23 ms / 87k QPS;  cuBLAS 0.11 ms / 181k QPS
#   N=100k: wlasny kernel 1.78 ms / 11.2k QPS; cuBLAS 0.95 ms / 21k QPS
#   N=1M:   wlasny kernel 14.4 ms / 1.39k QPS; cuBLAS 7.89 ms / 2.53k QPS
#   P95 latencji 1 zapytania: N=100k ~1.85 ms, N=1M ~14.3 ms.
# ============================================================================
